nix_webserver

Plataforma Django/DRF multi-tenant que roda o back-office completo de gestores de patrimônio: ingestão de movimentações, conciliação contra custodiantes, cálculo de posições, agregação em portfólios, geração de relatórios ao cliente e cobrança — com uma camada agêntica de LLMs operando por cima de tudo isso.

§01

Topologia de runtime

Um único artefato — a imagem linux/arm64 construída a partir de pipeline/docker/production.Dockerfile (Python 3.11-alpine, com as libs nativas do WeasyPrint para gerar PDF) — sobe como cinco serviços ECS Fargate distintos, que se diferenciam apenas pelo comando. O front-end é um projeto separado (portal_v2, React + TypeScript); este repositório é exclusivamente a API e os workers.

§02

O caminho de uma requisição

A ordem do middleware é carga estrutural, não detalhe. O tenant é resolvido antes de qualquer outra coisa, porque todo middleware seguinte precisa rodar com o schema certo já ativo; e o contexto de RLS é definido pela autenticação, de modo que a política do banco já esteja armada quando o ORM emitir a primeira query.

§03

Multi-tenancy e Row-Level Security

Existem duas forças de isolamento diferentes convivendo no mesmo banco, e a distinção decide como qualquer query deve ser escrita. Multi-Family Offices ganham schema próprio via django-tenants — isolamento duro, e um acesso cruzado tende a falhar de forma barulhenta. Consultores, ao contrário, moram todos juntos no tenant compartilhado revertai: ali não existe separação por schema, e a única fronteira entre um consultor e outro é a RLS.

§04

O caminho do dinheiro

O pipeline financeiro tem uma inversão que precisa estar clara antes de qualquer alteração: hoje a Nix não calcula posições. Ela empurra os trades para a Comdinheiro e puxa de volta as posições calculadas. A conciliação envolve esse ida-e-volta para garantir que o lado Nix e o lado do custodiante concordem antes de os números seguirem adiante.

§05

Processamento assíncrono

Uma fatia enorme do processamento roda em Celery, e o app async_tasks não é "a fila": é controle de admissão. Antes de qualquer mensagem chegar ao broker, um queue manager decide se aquele trabalho já está em andamento, se está bloqueado por falhas repetidas, e em qual fila ele cabe.

Resultados vão para o banco via django-celery-results, com acks_late, prefetch=1 e teto global de 30 min por task.

§06

Superfície agêntica e mensageria

Boa parte do produto existe para que agentes de LLM operem o back-office. São dois subsistemas distintos: mensageria (a conversa entre o investidor e o agente, canal-agnóstica) e trabalho de agente (tarefas despachadas para agentes nomeados — Maia, Curator, Bushido, PACMAN, Concierge).

Documentação como parte do código

Cada app tem um doc otimizado para LLM em _bmad-output/app_docs/<app>.md com modelo de dados, serviços, endpoints, eventos, dependências cruzadas e raio de dano. Atualizá-lo no mesmo PR é obrigatório, e há um workflow (docs-freshness.yml) que checa se ficou para trás. Fluxos que nenhum app sozinho possui vivem em workflows_docs/ — o pipeline de posições, cada calculadora financeira, a geração de relatórios e o mergulho em RLS.

Regra de acoplamento

Conector é transporte burro. Chamar um conector direto é considerado code smell: ele só deve ser invocado de dentro de uma classe de serviço que é dona de uma operação específica — importar posições passa por ComDinheiroPositionsImporter, encapsulado por ImportPositionsCommand; enviar e-mail passa por Communicator, que também escreve o CommunicationLog. Isso é o que torna o provedor substituível trocando uma classe, e não todos os pontos de chamada.

§09

Segurança

Autenticação

JWT via simplejwt com rotação e blacklist após rotação (access 72 h, refresh 1 dia em produção). A classe padrão de autenticação é a de impersonation, que grava o persona atuante nos GUCs de sessão. Backend por e-mail, com django-axes na frente: 10 falhas por IP, cooloff de 30 minutos. Permissão padrão é DjangoModelPermissions.

Superfícies não autenticadas

São poucas e todas contidas: o formulário de leads da landing (ticket de sessão de uso único + rate limit em Redis compartilhado + kill switch por env), o link do relatório ao cliente (autenticado por prefixo de CPF/CNPJ) e dois webhooks de custodiante — um com HMAC comparado por compare_digest, outro protegido por URL não adivinhável mais allowlist de IP no nginx.

Segredos e PII

Segredos de provedor ficam em ExternalCredential, criptografados com Fernet por tenant, lidos por get_secret_value. Em produção, tudo vem do NIX_SECRET no Secrets Manager, cujas chaves são listadas dinamicamente para montar o secrets[] da task definition — o que elimina drift entre o repositório e a AWS.

Entrada de agente

Tráfego de agente entra por um header opaco convertido em JWT impersonado. O nome do header é sanitizado antes do uso (padrão + blacklist), credencial inválida falha com 401, e is_safe=False é um kill switch pegajoso que bloqueia a saída até um operador reverter. Todo texto de entrada passa pelo screen de prompt injection.

§10

Entrega

GitHub Actions faz tudo — o .circleci/config.yml ainda existe no repositório, mas está inteiramente comentado. O invariante central é build-once: a imagem é construída uma vez, taggeada com o SHA, e as promoções para staging e produção apenas re-taggeiam esse mesmo digest no ECR. Só um hotfix cujo commit não passou por staging dispara um build novo.

§11

Convenções que o código presume

Arquitetura

OOP com cebola: ViewSet → Serializer → Service → Model, dependências sempre para dentro. Modelos herdam BaseModel; endpoints são ViewSets registrados no router; regra de negócio só em classes dentro de service/. Herança segue "filho magro, mãe gorda" — o comportamento sobe para a base.

Integridade

Decimal para dinheiro, nunca float. FK com PROTECT ou SET_NULL, nunca CASCADE. Enums como TextChoices, um por arquivo. Migrations sempre geradas pelo Makefile. Transações curtas e só para múltiplas escritas.

Testes

Todo teste estende NoExternalTestCase, que bloqueia conexão externa e cria um tenant de teste. Fábricas com factory_boy. Um teste que não pode falhar por bug de regra de negócio é custo de manutenção, não cobertura.

Fluxo de trabalho

O repositório desenvolve pelo BMad Method: análise e planejamento opcionais, mas solutioning e implementação obrigatórios, com dois portões de padrões em volta da implementação. A única exceção é um hotfix crítico verificado. Fuso do projeto é BRT, não UTC.

Antes de mudar qualquer coisa

Raio de dano não é tamanho de diff. Três linhas num ponto central podem ser sistêmicas, enquanto uma feature isolada de 800 linhas é contida. A pergunta que precisa ter resposta é se a coisa quebra alto — com exceção visível — ou baixo: um número errado, sem rastro, num relatório que já foi enviado ao cliente.
